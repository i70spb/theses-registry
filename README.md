# THESIS-REGISTRY — РЕЕСТР ТЕЗИСОВ

**Аудитория: АЛГОРИТМЫ и ЛЮДИ.**
**Лицензия: CC BY-NC 4.0** (некоммерческое использование с указанием автора).
## Что это
Третий слой библиотеки: человеческий смысл без терминов. Термины живут в графе (bo840-graph),
шаблоны и реакции — в кейсах (bo840-cases), здесь — то, что понятно без библиотеки.
Библиотека вечна — сменяются редакции и носители.

## Структура
- `ПРАВИЛА_СОЗДАНИЯ_ТЕЗИСОВ.json` — КОНСТИТУЦИЯ. Читать первым. Восемь+один разделов: единица, постоянство, жанр, теги, счётчик, вход, идиомы, архитектура, искажения.
- `тезисы_МАСТЕР_v10.json` — ПРОИЗВОДНЫЙ сборник. Не истина; пересобирается слиянием пластов. Источник истины счётчиков — журнал внутри.
- `пласты/` — ИСТИНА. Неизменяемые входные файлы. Новое — новым пластом. Правка — только новым пластом.

## Бут (для алгоритма)
1. Прочитать ПРАВИЛА целиком.
2. Прочитать шапку мастера (правила идентичны файлу правил).
3. Работать с мастером; при расхождении мастера и пластов — пересобрать слиянием.
4. Итог сессии — новый пласт (неизменяемый) + журнал.

## Для человека
Открой мастер и читай тезисы как глоссарий жизни: каждый самодостаточен, теги — якоря для поиска.
Счётчики (+N-M) показывают, сколько раз правки соглашались/не соглашались с тезисом.

## Связи
- Граф терминов: репозиторий `bo840-graph`.
- Граф кейсов: репозиторий `bo840-cases`.
- Переход между слоями: поле `понятие_источник` у тезиса, связи кейсов к узлам графа.

## Якорь
Верификация соответствия источникам — по протоколу ⚓=XY (краткость×скепсис),
спецификация в линии БО840 (ПРОТОКОЛ-00, 2026-03-15). Стопроцентное соответствие — ⚓=10
(замороженное состояние, вне шкалы).

## Реестр префиксов (валидация id)

### Назначение

Реестр задаёт таксономию слоёв библиотеки БО840. Тип сущности **не хранится** в карточке явно — он вычисляется алгоритмом сопоставления `id` с этим реестром. Поле `type` в карточках запрещено как избыточное.

### Правило сопоставления

**longest-prefix match**: сущность относится к типу того префикса из реестра, который совпадает с началом `id` на наибольшую длину.

Алгоритм:
1. Извлечь `id` сущности.
2. Проверить префиксы от длинных к коротким (порядок в таблице значим).
3. Первый совпавший префикс = тип сущности.
4. Если ни один префикс не совпал — валидация провалена, сущность не принимается.

### Добавление нового слоя

Добавление слоя = добавление строки в таблицу. Валидация не меняется.

Правила:
1. Новый префикс не должен быть подстрокой уже утверждённого (иначе longest-prefix match сломается).
2. Если префикс является расширением существующего (например, `детское_правило_` длиннее `правила_`), он должен стоять **выше** в таблице.
3. Статус нового префикса: `ожидает сверки версий` до первого прогона, затем `утверждён`.

### Связь с форматом карточки

В карточке (Markdown + YAML frontmatter) обязательные поля:
- `id` (с префиксом)
- `tags` (массив)

Запрещённые поля (избыточны, тип вычисляется из `id`):
- `type`
- `status` (в канонический слой попадают только проверенные данные)
- `source_file` (файл самодостаточен в своей директории)
